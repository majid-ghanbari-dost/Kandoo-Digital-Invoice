## 1. Purpose and scope

WP-10.1 delivers ONE deterministic Digital Invoice Lifecycle mechanism: a
durable, append-only, tamper-evident lifecycle register that attaches ONE
Digital Invoice (INV-DI-1:1) to an ISSUED Canonical Invoice (P6.2) and records
its progression through the frozen lifecycle vocabulary

    DRAFT → EXTRACTED → VALIDATED → ISSUED → REVOKED | SUPERSEDED

quoted VERBATIM from the PO mission dispatch (AS-03 — no other state exists
here). Every lifecycle movement is an EXPLICIT act, fail-closed, verified
against the LIVE P6.2 verified read + whole-chain trace at act time, recorded
as an immutable event with a per-invoice monotonic sequence, and projected
deterministically: the current state of a Digital Invoice is a pure function
of its event chain. Nothing is automatic — no automatic issuance, no
automatic revocation, no automatic supersession, no time-based transition, no
content-driven transition.

Terminology note (normative): P6.2's "invoice_id Issuance" issued the
IDENTITY (the D-02 Canonical Identity). The ISSUED lifecycle state here is
the OPERATIONAL issuance act of the Digital Invoice — a lifecycle state of
the frozen dispatch vocabulary, not a second identity issuance. This layer
mints no identifier (AST-proven).

In scope:
1. **Entry (open)** — open ONE Digital Invoice per issued Canonical Invoice,
   through the P6.2 verified read + the P6.2 whole-chain trace, consumed
   never bypassed (§4).
2. **The lifecycle state machine** — the frozen vocabulary verbatim + the
   declared transition matrix (§5): linear progression DRAFT → EXTRACTED →
   VALIDATED → ISSUED; terminal acts REVOKE / SUPERSEDE from ISSUED only; NO
   backward, skip, or terminal-exit transitions (DB CHECK-enforced).
3. **Lifecycle acts** — mark_extracted / mark_validated / issue / revoke /
   supersede: explicit, idempotent, fail-closed, zero-residue-on-refusal
   (§5).
4. **Verified reads + trace** — own-row VOR, event-chain integrity
   (per-invoice seq, from/to chain closure), linked P6.2 re-verification,
   anchor cross-checks, supersede-replacement re-verification, and the
   lifecycle trace that adds ONE head link onto the intact P6.2 chain (§6).
5. **Persistence** per the project store pattern (§7/§8): separate SQLite
   file, synchronous=FULL, atomic commit, append-only (no UPDATE/DELETE),
   sha256-v1 fingerprints via the project S1 service, CHECK + UNIQUE gates,
   restart-safe, tamper-evident.
6. Behavioral + structural boundary tests (§12).

Out of scope (FORBIDDEN — boundary of this WP): any presentation, rendering,
display-format, or delivery-channel work (WP-10.2 / DEF5 — PO-deferred); any
change to any frozen layer P1–P9 (purely additive WP); canonicalization
re-decision of ANY kind (P6.1 owns it); canonical assembly or invoice_id
handling (P6.2 owns it); REVIEW queue operations (P5.2/P6.1 own their
queues); native Sale or native Invoice domain creation (AS-02 chain remains
upstream-owned; DEF1 — external capture never creates a Sale); customer
linking/creation semantics (WP-9.1/D-06/DEF3); product matching (WP-8.1);
fuzzy/semantic/AI matching of ANY kind; inventory effects (AD-03); currency/
tax interpretation (no currency surface exists in the implemented canonical
record — adding one would be invention; IRR remains a Canonical Invoice v1
frozen vocabulary item quoted, not implemented, here); OCR/Holoo/Cloud/UI/
mobile; any automatic lifecycle behavior of any kind.

## 2. Input path (normative)

The ONLY invoice path is the P6.2 public service surface:
`CanonicalAssemblyService.read_assembled_invoice` (VOR) for the issued
Canonical Invoice, and `CanonicalAssemblyService.trace_assembled_invoice`
for its whole-chain verification (which re-walks the P6.1 admission, the
gate decision, the P5.2 domain state, the P5.1/P4.2/P4.1/P3.2/P3 layers and
Capture S1 inside one call). Both are consumed VERBATIM — never bypassed,
never re-implemented, never triggered for upstream execution (spy-proven).
This layer never reads any upstream store directly, never reads raw
artifacts, never computes canonical content, and never accepts invoice facts
from any source other than the P6.2 outcome objects.

Scope of one lifecycle request = ONE issued Canonical Invoice identified by
its `invoice_id` — the D-02 Canonical Identity, consumed verbatim. There is
no second request vocabulary.

## 4. Open ladder (normative — fail-closed, ordered)

- O1  P6.2 verified read of the issued Canonical Invoice — unknown/refused
      → `DigitalInvoiceRequestRefused` (detail propagated verbatim);
      integrity failure / verification unavailable →
      `DigitalInvoiceInputIntegrityFailure` (fail-closed passthrough;
      Issue Report on unavailable).
- O2  P6.2 whole-chain trace (`trace_assembled_invoice`) must succeed —
      consumed, never bypassed; any broken link →
      `DigitalInvoiceInputIntegrityFailure` (no broken chain silently
      accepted).
- O3  Replay (INV-DI-1:1): a Digital Invoice already exists for this
      invoice_id → the existing record is returned VERBATIM after its own
      full verified read (§6) — `DigitalInvoiceOpenReplay`, ZERO new rows
      (D-03: replay never re-decides/never duplicates).
- O4  Atomic commit of the creation row (state DRAFT by construction):
      collision on the UNIQUE(invoice_id) backstop → re-read the winner and
      return `DigitalInvoiceOpenReplay` (concurrency safety; DB uniqueness
      as the final backstop — never Python-only).

Exhaustive open ladder (never silent): `open_digital_invoice` →
DigitalInvoiceOpened | DigitalInvoiceOpenReplay | DigitalInvoiceRequestRefused |
DigitalInvoiceInputIntegrityFailure | DigitalInvoiceStorageUnavailable.

## 5. The lifecycle state machine + acts (normative)

### 5.1 Vocabulary (AS-03 — VERBATIM, exhaustive)

    DRAFT | EXTRACTED | VALIDATED | ISSUED | REVOKED | SUPERSEDED

No other state exists; no synonym, alias, or sub-state is introduced
(AD-04/CL-1). DRAFT is the state at open (the creation row records it
implicitly — OD-DI-E); every other state is reached ONLY through a recorded
lifecycle event.

### 5.2 Transition matrix (declared per D-09 — OD-DI-D)

The frozen vocabulary is an ORDERED lifecycle; the declared matrix is its
minimal deterministic reading — each state's unique legal predecessor, and
the two terminal acts of an ISSUED document:

    #  event_type      from_state   to_state     anchor
    E1 MARK_EXTRACTED  DRAFT        EXTRACTED    §5.3
    E2 MARK_VALIDATED  EXTRACTED    VALIDATED    §5.3
    E3 ISSUE           VALIDATED    ISSUED       §5.3
    E4 REVOKE          ISSUED       REVOKED      §5.4
    E5 SUPERSEDE       ISSUED       SUPERSEDED   §5.4 (replacement required)

Structural properties (enforced by SQL CHECKs + defensive Python mirrors +
AST/behavioral tests):
- Linear progression: each state has EXACTLY ONE legal predecessor; each
  non-terminal state has EXACTLY ONE outgoing transition.
- Terminal states REVOKED / SUPERSEDED have NO outgoing transition (nothing
  follows a terminal act — the frozen vocabulary defines no further state).
- NO backward transition, NO skip transition (DRAFT → ISSUED is refused),
  NO transition outside the matrix — a refused act leaves ZERO durable
  residue.
- REVOKE and SUPERSEDE are mutually exclusive per document (both act from
  ISSUED; whichever commits first makes the other refused — terminal
  discipline). This also makes supersession cycles structurally impossible:
  a replacement must be ISSUED (§5.4), and a superseded source is never
  ISSUED again.
- NOTHING is automatic: every event exists ONLY as the result of one
  explicit service act verified against the LIVE P6.2 chain at act time.

### 5.3 Progression acts (E1–E3)

Each act, in order:
- A1  the Digital Invoice must exist (else `LifecycleRequestRefused`,
  `no-digital-invoice`, zero residue);
- A2  the Digital Invoice's full verified read must succeed (§6) — a
  tampered own row, a broken event chain, or a failed linked P6.2
  re-verification withholds the act (`LifecycleInputIntegrityFailure` /
  VerificationUnavailable passthrough);
- A3  projected current state:
      - == target state → `LifecycleReplay` (verbatim, ZERO new rows; the
        act is a replay of an already-recorded fact — D-03);
      - == the matrix predecessor → advance (E4 commit below);
      - anything else → `LifecycleRequestRefused` naming the current state
        and the expected predecessor (`lifecycle-transition-unavailable` —
        skipping, backward movement, and terminal-exit attempts are all this
        refusal);
- A4  atomic commit of ONE event row as a COMPARE-AND-SWAP append (§8
      OD-DI3): the in-transaction guard re-reads the live chain — the
      event's per-invoice seq must equal the live chain length and the live
      projected state must still equal the event's from_state; commit-time
      CAS rejection (a concurrent same act won) → re-project honestly →
      `LifecycleReplay`; a concurrent OPPOSING terminal act won (REVOKE vs
      SUPERSEDE race) → the state is now terminal and the act is
      `LifecycleRequestRefused` (honest refusal — never reshaped).

The progression acts carry NO content of their own: the extraction fact
(E1) and the validation fact (E2) are re-proven LIVE at act time by the
A2 verified read (the P6.2 read + whole-chain trace re-verify the canonical
content, the admission linkage, and the whole upstream chain to Capture S1
— the SAME verification discipline for every act; no threshold, no extra
condition, nothing invented). The act records the lifecycle stage; the
verification proves the underlying frozen facts still hold.

### 5.4 Terminal acts (E4–E5)

- REVOKE — explicit withdrawal of an ISSUED Digital Invoice; terminal.
- SUPERSEDE — explicit replacement of an ISSUED Digital Invoice by ANOTHER
  Digital Invoice in the register; terminal. Verification ladder at act
  time (beyond §5.3 A1–A4): the replacement must (i) exist in the register,
  (ii) pass its OWN full verified read, (iii) be in projected state ISSUED,
  (iv) differ from the source (self-supersession refused). A SUPERSEDE
  replay additionally requires the declared replacement to byte-match the
  recorded one — a different replacement on replay is refused
  (`supersede-replacement-conflict`; OD-DI-H — the WP-6.2 OD-A8 discipline).
  The replacement is stored as a POINTER (its invoice_id) — never copied,
  never merged, never suppressed.

### 5.5 Idempotency & determinism

- Every act is idempotent at its target state (replay verbatim, zero rows).
- The projected current state is a PURE function of the event chain
  (fold in per-invoice seq order; DRAFT when no events) — proven by
  cross-stack rebuild determinism tests.
- No clock, counter, or environment value ever influences a transition
  decision; timestamps and uuid4 hex ids are bookkeeping only
  (project-wide pattern).

## 6. Verified reads + trace (normative)

`read_digital_invoice` / `read_digital_invoice_by_id` — definitive integrity
verdict computed INSIDE the read:

1. Own-row VOR (creation row, sha256-v1 record fingerprint — tampered rows
   withhold content, never served).
2. Event-chain integrity: every event row's own VOR; per-invoice seq
   gap-free ascending from 0 (a gap → VerificationUnavailable); chain
   closure (first event from_state == DRAFT; event[k].from_state ==
   event[k-1].to_state; every (event_type, from, to) inside the §5.2
   matrix); the projected current state is computed and returned.
3. Linked P6.2 re-verification: the linked Canonical Invoice MUST verify
   through the P6.2 verified read; the copied anchor set (capture_s1,
   capture_s1_algorithm_id, capture_id, document_id, origin) MUST equal the
   verified record's (anchor drift → VerificationUnavailable — a forged or
   half-written row cannot pass).
4. SUPERSEDE events re-verify their replacement ONE level deep: the
   replacement exists and passes its own verified read (own VOR + its event
   chain + its linked P6.2 invoice). NO state condition at read time: the
   ISSUED precondition is an ACT-time rule (§5.4) — the replacement's own
   subsequent lifecycle (e.g. being superseded again in a correction chain
   a→b→c, or revoked) is its own durable fact and NEVER withholds the
   source's recorded history (a read must not depend on WHEN it happens —
   determinism; OD-DI-I, the WP-7.2 OD-DF-D discipline).
5. Shape gates mirroring every storage CHECK.

Outcomes (exhaustive): DigitalInvoiceReadSuccess (record + projected
current_state + events + verified P6.2 read + verified_at) |
DigitalInvoiceReadIntegrityFailure | DigitalInvoiceReadRefused (no such
Digital Invoice) | DigitalInvoiceReadVerificationUnavailable.

`trace_digital_invoice` — ONE head link onto the intact P6.2 chain: own
verified read (steps 1–4) + the P6.2 whole-chain trace consumed VERBATIM +
ordered coarse link verdicts (no source values copied). Outcomes:
DigitalInvoiceTraceSuccess | DigitalInvoiceTraceIntegrityFailure |
DigitalInvoiceTraceRefused | DigitalInvoiceTraceVerificationUnavailable.

## 8. Persistence & invariants (same store pattern as P1–P9)

- OD-DI1 storage: stdlib sqlite3, ONE separate embedded DB file
  (`digital-invoice.db`); `synchronous=FULL`; idempotent schema; explicit
  BEGIN IMMEDIATE / COMMIT.
- OD-DI2 atomic commit: one creation row or one event row per transaction —
  zero residue on any failure, by construction.
- OD-DI3 invariants: INV-DI-1:1 (at most ONE Digital Invoice per
  invoice_id — in-transaction check + UNIQUE backstop); per-invoice event
  seq strictly gap-free ascending — committed as a COMPARE-AND-SWAP append:
  inside the transaction the caller's event_seq must equal the live chain
  length AND the chain's live projected state must still equal the event's
  from_state (a stale-state append can never persist — stronger than a
  UNIQUE(seq) backstop alone); the §5.2 matrix (CHECK-enforced); terminal
  discipline (no event may follow a terminal event — enforced by the matrix
  via the from_state chain: no legal event has from_state ∈ {REVOKED,
  SUPERSEDED}).
- OD-DI4 ids/clock: digital_invoice_id / event_id = uuid4 hex — bookkeeping
  only; NO identity is minted in this layer (the invoice_id is consumed
  verbatim — D-02); single layer clock (UTC ISO-8601).
- OD-DI5 integrity anchors: `record_fingerprint` = sha256-v1 over the row
  scalars (canonical fixed-order serialization, computed via the project S1
  service — no hashlib in the layer), verified INSIDE every read (VOR).
- OD-DI6 storage gates: SQL CHECKs (§7) + defensive Python-side commit
  refusals mirroring every CHECK.
- OD-DI7 no update/delete: creation rows and event rows are immutable once
  committed; no UPDATE or DELETE path exists in this store (AST-proven);
  restart-safe; tamper-evident.

- OD-DI-J pointer discipline: NO canonical invoice value (number, date,

- OD-DI-K listing discipline: `digital_invoices()` / `lifecycle_events()`

  implemented here — AS-04).
