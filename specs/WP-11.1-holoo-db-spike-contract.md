Status:      ACTIVE — binding for WP-11.1 implementation
Authority:   REG-WPR Phase Index P11 «WP-11.1 Holoo DB Spike (read-only; startable after G1 — G1 PASS)»
             + Mission dispatch «HOLOO INTEGRATION — READ-ONLY SPIKE» (PO, 2026-10-08)
             + Decision Register D-04 (FROZEN), AD-01, AS-01, D-09
Upstream:    capture (S1 service — the project's single hash capability)
Downstream:  NONE. The spike writes to nothing and feeds nothing. D-04: "Spike فقط گزارش می‌دهد"

## §1 Purpose

WP-11.1 proves — in the strict READ-ONLY boundary of the dispatch and FROZEN
D-04 — that Kandoo CAN (a) open a Holoo-shaped database file without any
possibility of mutating it, (b) discover its schema, (c) validate a DECLARED
field mapping against the discovered schema fail-closed, and (d) extract
candidate invoice/customer/product rows into a deterministic, provenance-
preserving SPIKE REPORT for the Product Owner / Technical Manager.

The spike is an instrument, not a pipeline stage. Its only output is a report.
The report is NOT a Kandoo domain object: it never enters Capture,
Reconstruction, Extraction, Normalization, Canonicalization, Validation,
Canonical Assembly, or Digital Invoice layers, and it never becomes a `Sale`
(DEF1), a Customer (DEF3/D-06), or Canonical truth without the Frozen gates
(AD-01/AS-01: Holoo data reaches Canonical only through the full External
Flow pipeline — a later, separately-dispatched decision space).

## §2 Normative boundaries (READ-ONLY discipline — absolute)

The implementation MUST NOT, under any code path, argument, or failure mode:

1. Execute INSERT, UPDATE, DELETE, DROP, ALTER, CREATE, REPLACE, VACUUM,
   ATTACH, DETACH, REINDEX, or any other mutating SQL against the source.
2. Open the source in any mode other than read-only (`mode=ro` URI).
3. Rely solely on one enforcement layer: enforcement is a LADDER (§6) —
   engine-level refusal, connection-level `PRAGMA query_only`, a runtime SQL
   read-guard, and structural (AST) probes PLUS byte-level proofs.
4. Create, modify, or delete ANY file in or beside the source database
   (including SQLite side files: `-wal`, `-shm`, `-journal`).
5. Change Digital Invoice state, create Kandoo Sales, mutate inventory or
   accounting truth, or write back to Holoo (DEF1, AD-03, D-04).
6. Let ANY value extracted from Holoo become, or be stored as, Canonical /
   domain state. Report-only (D-04).
7. Guess a Holoo schema. Schema knowledge enters the system ONLY as an
   operator-declared mapping (§5) validated against the discovered schema,
   fail-closed. No built-in table/column names, no heuristic discovery of
   "the invoice table".
8. Introduce a second identity algorithm, canonicalization logic, or hash
   capability. Source hashing reuses the capture S1 service exclusively.
9. Require network access, external services, drivers, or non-stdlib
   dependencies (offline-safe; stdlib-only per project pattern).

## §3 Vocabulary (report-only labels — never domain semantics)

Selection roles (declared by the operator, recorded verbatim in the report):

```text
INVOICE_CANDIDATE_HEADER | INVOICE_CANDIDATE_LINES |
CUSTOMER_CANDIDATE | PRODUCT_CANDIDATE | OTHER
```

These labels describe what the OPERATOR declared about a selection's intended
inspection role. They carry no domain behavior, no lifecycle, no identity, and
no authority. They exist so the report is self-describing; downstream
enrichment semantics (WP-11.2 territory) are explicitly NOT decided here.

Mapping validation statuses: `MAPPED_OK` | `MAPPING_REFUSED`.

## §4 Source model

The spike reads ONE SQLite database file supplied by the operator
("the source"). Rationale (declared delegated decision, OD-HS-A): the Holoo
DB Spike per the Phase Index investigates a database-shaped source offline;
file-based SQLite is the only engine that satisfies offline-safe + stdlib-only
+ determinism in this MVP. Adapters to live DB engines (ODBC/SQL Server),
network sources, or Holoo application APIs are OUT OF SCOPE (they are WP-11.2
territory and require PO decisions — §14).

The source is treated as an opaque byte sequence with a schema: the spike
records its SHA-256 (via capture S1 service) at open and at close and proves
the two equal (§6 L5). The spike NEVER assumes the source is genuinely from
Holoo: the mapping validation is what connects a declared inspection intent to
a discovered schema, and it must be re-declared for every real source.

## §5 Declared mapping (fail-closed)

A `HolooSelection` is the unit of declared intent:

```text
name        : unique selection name (unique across the mapping — duplicates refused)
role        : one of §3 roles
table       : table name (verbatim identifier; quoted safely, never interpolated raw)
columns     : projected column names (must ALL exist in the discovered schema)
order_by    : uniqueness-bearing column list for deterministic row order
              (must ALL exist; required — no declared order_by → MAPPING_REFUSED)
max_rows    : per-selection extraction cap (§8)
```

Validation against the discovered schema, per selection:

- table not found → `MAPPING_REFUSED` (reason lists the discovered table names —
  no case-folding guessing, no fuzzy match);
- any declared column missing → `MAPPING_REFUSED` (reason lists missing names);
- `order_by` missing/empty or referencing unknown columns → `MAPPING_REFUSED`;
- duplicate selection `name` → hard `MappingRefused` exception (mapping-level
  defect, whole request refused — mirrors the project's UAC discipline).

Refused selections contribute NO rows. They appear in the report with their
refusal reason (the report is the spike's honest finding — a refusal is a
result, not a crash). Unusable SOURCES (missing file, non-SQLite bytes,
unreadable file) are hard failures: no report at all (§11).

## §6 Read-only enforcement ladder (defense in depth)

| L | Layer | Mechanism | Proof obligation |
|---|---|---|---|
| L1 | Engine | SQLite URI `mode=ro` — the engine itself refuses writes | connection `PRAGMA query_only` read-back = 1; write attempts through the same connection raise |
| L2 | Connection | `PRAGMA query_only = ON` set at open | read-back evidence recorded in the report |
| L3 | Runtime guard | every service-issued SQL string passes `_assert_read_only_sql`: single statement; first token SELECT or whitelisted read-only PRAGMA; no comments; no parameter-bearing SET pragmas; whole-word ban list (INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/REPLACE/VACUUM/ATTACH/DETACH/REINDEX/INTO/writable_schema/load_extension/readfile/writefile/PRAGMA-in-SELECT/WITH) | refusal tests via guard; guard verdicts recorded as `ReadOnlyViolation` |
| L4 | Structure | AST probes over the whole production package: zero mutating SQL keywords in ANY string constant, zero `.commit(` / `.executescript(` / `.executemany(` calls, import allowlist (stdlib + capture + relative only), `mode=ro` and `query_only` literals present | test suite |
| L5 | Bytes | source SHA-256 (S1) + file size + mtime_ns + SQLite header change-counter (file bytes 24..27) + full directory listing of the source's parent, captured before and after every service run and asserted equal | byte-proof tests, including a no-side-files assertion |

The report itself carries `source_sha256_at_open` and `source_sha256_at_close`;
the service refuses to emit a report if they differ (`ReadOnlyViolation`) —
a mutated source can never produce a clean-looking report.

## §7 Introspection

Schema discovery uses ONLY whitelisted read PRAGMAs: `PRAGMA table_list` for
tables (internal `sqlite_%` objects are excluded from the mapping namespace and
counted separately in the report), `PRAGMA table_info("<table>")` for columns
(name, declared type). Discovery output is sorted by name — the report is a
sorted, deterministic projection of the schema, never a live handle.

## §8 Extraction (deterministic projection)

Per valid selection, exactly two SQL statements (both guard-passed, both
recorded verbatim in the report):

1. `SELECT COUNT(*) FROM "<table>"` → `source_row_count`
2. `SELECT "<c1>", "<c2>", ... FROM "<table>" ORDER BY "<o1>", "<o2>", ... LIMIT <max_rows>`

Rules:
- identifiers are always wrapped in double quotes with internal quote doubling
  (no identifier is ever interpolated raw; no VALUES/parameters exist anywhere —
  full-table projection only, no WHERE);
- `source_row_count > extracted_row_count` ⇒ `truncated = true` in the report
  (fail-loud, never silent);
- rows are encoded through the deterministic type-tagged encoder (§9) — no
  type coercion, no reformatting, no inference (provenance-preserving);
- row order is fully determined by the declared `order_by`.

## §9 Deterministic value encoding

SQLite storage classes map to tagged pairs — byte-stable across runs and
platforms:

```text
NULL    → ["N", null]
INTEGER → ["I", <int as decimal>]          (full precision — no float collapse)
REAL    → ["F", "<float.hex()>"]          (exact bit-level value as hex string)
TEXT    → ["T", <string verbatim>]        (unicode preserved)
BLOB    → ["B", "<base64 of exact bytes>"]
```

## §10 The report (the spike's ONLY output)

`HolooSpikeReport` — a frozen dataclass with a canonical JSON serialization
(`sort_keys=True`, `ensure_ascii=False`, `indent=2`, trailing newline):

```text
spec_id / spec_version
source_label            (operator-declared label; the spike never invents one)
source_size_bytes
source_sha256_at_open / source_sha256_at_close / s1_algorithm_id   (sha256-v1 via capture S1)
sqlite_version, read_only_uri, query_only_readback
discovered_table_count, discovered_internal_object_count
discovered_tables       (sorted: name + sorted column names/types)
mapping_validations     (sorted: name/role/table/status/reason)
extractions             (only MAPPED_OK selections, sorted by name:
                         source_row_count, extracted_row_count, truncated,
                         columns, order_by, rows)
sql_statements_used     (ordered, verbatim — full auditability)
no wall-clock time, no random values, no environment probes anywhere
```

The report object and its JSON are the deliverable consumed by humans (PO/TM).
No API, no persistence, no downstream wiring exists (§2.6).

## §11 Failure semantics (fail-closed, honest)

Hard failures (exception; NO report produced):
- `HolooSourceUnavailable` — source path missing, is a directory, or unreadable;
- `HolooSourceNotSqlite` — file exists but is not a SQLite database
  (header/integrity probe fails);
- `MappingRefused` — duplicate selection names (mapping-level defect);
- `ReadOnlyViolation` — guard refused a statement, or source hash changed
  between open and close (never expected; proves the ladder by existing).

Soft refusals (RECORDED in the report; run continues):
- per-selection `MAPPING_REFUSED` with the precise reason (§5).

No failure is ever swallowed, defaulted, or guessed around (project
fail-closed pattern).

## §12 Testing obligations (dispatch §8 — binding)

- normal read path: fixture-backed end-to-end report; schema discovery;
  extraction correctness; ×2 byte-identical JSON (determinism);
- invalid input: duplicate selection names; unknown table; unknown column;
  missing order_by — all fail-closed, refusals explicit;
- unavailable source: missing file / directory / empty file / non-SQLite bytes;
- malformed source: valid SQLite file with zero matching tables → refusals
  recorded, zero fabricated rows;
- duplicate/replay: repeated runs identical; duplicate selection names refused;
- determinism: same source + same mapping → byte-identical report (twice);
- durability (spike sense): repeated runs leave the source byte-identical
  (L5 proofs: hash, size, mtime, header change-counter, directory listing);
- boundary cases: empty tables; NULL/INTEGER/REAL/TEXT/BLOB cells; unicode
  text; identifiers with spaces/quotes; truncation cap behavior;
- permission / read-only enforcement: INSERT/UPDATE/DELETE/CREATE through the
  production read-only connection MUST raise (engine layer proof); guard
  refusal for every mutating statement class (runtime layer proof);
- negative no-write proofs: L5 byte-equality after every interaction;
- AST probes (§6 L4): mutating keywords, forbidden calls, import allowlist,
  required literals (`mode=ro`, `query_only`), no hashlib/random/eval/exec in
  the package, no domain-sibling imports (contamination sweep);
- vocabulary sweep: §3 roles are the ONLY role values; no Sale/Customer/
  Canonical/REVIEW semantics in the package surface.

## §13 Delegated implementation decisions (declared per D-09)

- **OD-HS-A** — source engine for the MVP spike: local SQLite file via
  `sqlite3` (stdlib); live-engine adapters deferred (WP-11.2 / PO).
- **OD-HS-B** — read-only URI built with `urllib.parse.quote` on the resolved
  path; `uri=True`; `isolation_level=None` (autocommit — no write transactions
  exist to manage; reads only).
- **OD-HS-C** — runtime SQL guard is token-based and conservative; anything
  not explicitly allowed is refused. PRAGMA whitelist (read forms only):
  table_list, table_info, index_list, index_info, foreign_key_list,
  database_list, page_count, page_size, encoding, schema_version,
  data_version, user_version, quick_check, integrity_check, compile_options,
  query_only (read-back).
- **OD-HS-D** — source hashing exclusively via capture `S1Service`
  (`sha256-v1`); no hashlib in this package.
- **OD-HS-E** — report has NO timestamps (determinism beats provenance-of-
  when; the RUNNER may log time outside the report).
- **OD-HS-F** — default per-selection cap = 5,000 rows (spike safety bound
  against unknown-size sources; `truncated` + COUNT make the bound loud).
- **OD-HS-G** — role vocabulary is the fixed §3 five-label set (report labels
  only); unknown role at construction → ValueError (fail-closed at the edge).
- **OD-HS-H** — identifier quoting: double-quote with doubling; identifiers
  additionally rejected if they contain NUL or exceed 256 chars.
- **OD-HS-I** — internal `sqlite_%` objects: excluded from mapping namespace;
  counted in `discovered_internal_object_count` (visibility without usability).
- **OD-HS-J** — the package exposes no persistence of the report; `to_json_
  bytes()` is pure; writing the JSON to disk is the runner's act, outside the
  package.
- **OD-HS-K** — the synthetic fixture builder used by tests/smoke lives under
  `holoo_spike/tests/` (test infrastructure; it necessarily contains INSERTs
  and is NEVER imported by the production package — AST import-sweep proves
  the direction of the dependency).

## §14 Out of scope (FORBIDDEN — boundary of WP-11.1)

- Any write to Holoo (DEF1/AD-03/D-04); Sale creation; inventory/accounting
  mutation; Digital Invoice issuance or state change.
- Entry of ANY extracted value into the Kandoo domain (D-04: only the full
  External Flow pipeline AS-01 can carry Holoo data toward Canonical — and
  that wiring is WP-11.2+ / PO decision space).
- Holoo schema mapping decisions, source-authority decisions, synchronization
  semantics, automatic reconciliation, write-back design (WP-11.2 — STOP
  protocol; DEF6 precedent: source field mapping is Adapter detail for
  TM/PO).
- Live DB engine adapters (ODBC/SQL Server), network sources, Holoo app APIs;
  OCR/VLM; UI; cloud; retention/privacy values (DEF4); fuzzy/AI matching of
  any kind (D-08); automatic customer creation (D-06/DEF3).
- Any change to frozen layers P1–P10 (additive-only WP; new package only).
