## §1 Purpose

WP-12.1 builds the CORPUS ASSEMBLY MECHANISM of the P12 Pilot phase: a
deterministic, fail-closed, integrity-checked assembly service that produces
versioned corpora of clearly-marked SYNTHETIC pilot documents together with
their DECLARED ground-truth labels, and stores them durably under explicit
provenance.

The corpus exists because the frozen decisions name it as the calibration
input: D-07 (accuracy thresholds 99.9% / 99% / 50–70% act as calibration
placeholders "until ratification" by Pilot P12 / G4), D-08 (rounding tolerance
is a Calibration Parameter "determined with the corpus"), DEF2 (the REVIEW
operational matrix is "calibrated with the Pilot"). WP-12.1 assembles the
material; WP-12.2 runs calibration measurements over it; WP-12.3 (PO/G4) is
the ONLY place any threshold value may be ratified. This WP ratifies nothing,
changes no parameter, and measures nothing.

The assembled corpus is EVIDENCE/PILOT INPUT. It is not a domain object: it
never enters Capture/Reconstruction/Extraction/Normalization/Canonicalization/
Validation/Canonical Assembly/Digital Invoice as truth, never creates a Sale
(DEF1), a Customer (D-06/DEF3), an inventory effect (AD-03), or a Digital
Invoice, and never bypasses the Canonicalization Gate.

## §2 Normative boundaries (absolute)

1. SYNTHETIC ONLY. Every corpus entry carries `origin_role =
   SYNTHETIC_PILOT_FIXTURE` and the exact marking string (§4). Any other
   origin role is refused at construction, at the service boundary, and at
   the storage CHECK. No real-source intake exists in this WP (real corpus
   material intake is an operator/PO activity outside this mission).
2. NO production-domain effect. The corpus package must not import, call, or
   write ANY production domain store. Its only sanctioned import surface is
   stdlib + `capture` (S1Service — the single hash capability, no second
   hash).
3. NO production dependency on the corpus. No production package may import
   `corpus` (AST-swept over all sibling packages). The ONLY sanctioned
   consumer is WP-12.2's calibration layer (declared in SPEC-WP122-CAL) and
   the tests/smoke of this WP.
4. DETERMINISTIC and CLOCK-FREE. Generation, serialization, fingerprints,
   manifest assembly, and persistence are pure functions of the declared
   inputs (template_id, entry_count, seed_base). The corpus layer carries NO
   clock at all — no wall-clock column, no time import (OD-CA-J; stronger
   than the project's bookkeeping-clock norm, because corpus material is
   content-addressed pilot input and has no operational clock semantics).
5. FAIL-CLOSED. Unknown template, non-positive/oversized entry_count, bad
   seed, malformed labels, missing marking, duplicate content under a
   different declared id, tampered rows — every anomaly is an explicit typed
   refusal or integrity failure. Nothing is guessed, inferred, or silently
   repaired.
6. NO FUZZY MATCHING, no threshold evaluation, no accuracy arithmetic, no
   ratification logic in this WP (that is WP-12.2's measurement surface and
   WP-12.3's PO decision; D-07/D-08 remain placeholders).
7. APPEND-ONLY storage. No UPDATE/DELETE code path (AST-proven). Row-level
   integrity via sha256-v1 through the S1 service; verify-on-read; tampered
   rows are WITHHELD, never delivered.

## §3 Vocabulary

```text
Origin role (the ONLY value):  SYNTHETIC_PILOT_FIXTURE
Marking (exact string, stored on every row):
  "SYNTHETIC-PILOT-FIXTURE — NOT PRODUCTION DATA"
Label kinds:  VALUE (expected normalized value present)
              ABSENT (the field is expected to be absent downstream)
```

A corpus entry is a tuple of page parts (raw document bytes, the SAME shape
the frozen pipeline ingests) plus declared labels over ENGINE-VOCABULARY
field names (`invoice.number`, `invoice.date`, `total.net`, `tax.amount`,
`total.gross`, …). Labels are DECLARED GROUND TRUTH for calibration
comparison in WP-12.2; they carry no domain authority and are never written
to any production store.

## §4 Templates (declared generators — data, not behavior)

Each template is a declared, versioned generator producing (parts, labels)
deterministically from one entry seed. Entropy is derived EXCLUSIVELY by
iterated S1 digests over counter-tagged byte strings (no `random`, no
`hashlib` import, no time, no environment). Amounts are integer cents;
HALF_UP at the declared declared-rate boundary; documents carry canonical
decimal strings (the frozen R-D1 canonical form), with a seed-gated
EUROPEAN-GROUPING rendering variant for `total.net` (the label stays the
canonical form — the variant exercises normalization, the ground truth does
not change).

Declared templates (v1):

```text
kv-invoice-clean-v1          — well-formed invoice: number/date/net/tax
                               (NO printed gross line — the pipeline's
                               reference derivation computes total.gross;
                               a document-printed gross would engage the
                               frozen derivation output-present gate and
                               route the entry to the uncertainty path).
                               All labels VALUE.
kv-invoice-rounding-probe-v1 — number/date/net/tax plus a PRINTED gross that
                               deviates from net + tax by a seed-derived
                               ±1/±2-cent residual (the real-world
                               document-level rounding disagreement D-08
                               calibrates against; the printed gross also
                               engages the frozen output-present gate — the
                               entry's downstream route is uncertainty).
                               Labels declare the PRINTED values verbatim.
kv-invoice-review-probe-v1   — tax.amount line absent → the downstream pipeline
                               route is expected to hold uncertainty (D-01/D-08
                               territory). Label kind ABSENT for tax.amount.
```

Template invoice dates use a FIXED DECLARED date (2026-06-15) — chosen away
from the known date-sensitive flake's collision window (2026-10-08) and away
from all corpus dates of prior suites.

## §5 Deterministic serialization & content addressing

Canonical byte serialization (8-byte big-endian length prefixes, fixed field
order, domain-separated tags — the capture-aggregate pattern):

```text
entry canonical bytes   = "kandoo-corpus-entry-v1" | LP(template_id) |
                          u64(entry_seed) | u64(ordinal) |
                          u64(part_count) + per part LP(bytes) |
                          u64(label_count) + per label (sorted by
                          field_name) LP(field_name) | kind-byte |
                          LP(expected_value; empty iff ABSENT) |
                          LP(label_provenance) |
                          LP(origin_role) | LP(marking)
manifest canonical bytes = "kandoo-corpus-manifest-v1" | LP(template_id) |
                          u64(seed_base) | u64(entry_count) |
                          u64(entry_count) + per entry in ordinal order
                          u64(ordinal) | LP(entry_fingerprint) |
                          LP(origin_role) | LP(marking)
```

`entry_fingerprint` = S1 over the entry canonical bytes. The corpus version
id IS the manifest fingerprint (content-addressed): the same declared inputs
always produce the same version id; any difference in content produces a
different id. There is no caller-supplied version id to collide.

## §6 Storage (durable, append-only, verify-on-read)

Single SQLite file owned by the corpus layer (`corpus.db`), full project
store pattern: `synchronous=FULL`, `BEGIN IMMEDIATE`, atomic single-
transaction assembly (all entries + manifest or NOTHING), immutable rows
(no UPDATE/DELETE — AST-proven), per-row fingerprint (sha256-v1 via S1)
verified on EVERY read, CHECK constraints pinning origin_role/marking,
UNIQUE(corpus_version_id, ordinal) + UNIQUE(entry_fingerprint) backstops,
restart-safe. The corpus store is a PILOT store: it is never a production
domain store and is never opened by any production package.

## §7 Service semantics (assembly ladder)

```text
A1 declared-input validation   — template registered; entry_count int
                                 1..10000; seed_base int ≥ 0; else REFUSED.
A2 deterministic generation    — per-ordinal entry seeds and document/label
                                 material derived from (seed_base, ordinal);
                                 any generation anomaly → REFUSED.
A3 content addressing          — entry fingerprints; manifest fingerprint =
                                 corpus_version_id.
A4 idempotent persistence      — version id absent → ONE atomic transaction
                                 inserts all entries + manifest → ASSEMBLED.
                                 version id present → byte-identity check of
                                 every existing fingerprint → REPLAY (verbatim,
                                 ZERO new rows — D-03 discipline); any
                                 mismatch → integrity refusal (fail-closed).
A5 verified read               — manifest VOR + every entry VOR + manifest
                                 fingerprint recomputed over the read entries
                                 + count agreement → CorpusReadSuccess; any
                                 failure withholds the corpus explicitly.
```

## §8 Failure semantics (typed, honest, zero residue)

Typed exceptions only (no bare asserts, no silent passes): input refusal,
unknown template, storage unavailable, not-found, read integrity failure,
read refused, verification unavailable. A forced failure mid-assembly leaves
ZERO rows (the transaction is the residue gate). Every refusal names what
was refused and why — no fabricated content, no partial corpora presented as
valid.

## §9 Testing obligations (binding)

Dedicated suite (behavior, not line coverage): generation determinism (×2
byte-identical; distinct seeds → distinct corpora), template coverage
(clean/rounding/review), label↔document agreement (every VALUE label's
expected value is exactly the canonical rendering of the document's declared
value; EURO-variant documents carry canonical labels), persistence +
restart durability, verify-on-read tamper matrix (field flips, forged
hash-consistent rows, CHECK refusals via direct SQL, UNIQUE backstops),
replay idempotency (zero new rows), forced-failure zero residue, malformed/
empty/boundary inputs, AST probes (no `random`/`eval`/`exec`/`hashlib`
import; no UPDATE/DELETE; import allowlist stdlib+capture; no sibling
production import of `corpus` — swept across ALL production packages), no
wall-clock in fingerprints/manifests, vocabulary sweep (no Sale/Customer/
Inventory/DigitalInvoice semantics). Repeat dedicated tests ≥ 2 independent
runs. Smoke runner (cold-start, 8 steps). Full regression + additive-only
frozen-integrity proof.

## §10 Delegated implementation decisions (declared per D-09)

```text
OD-CA-A storage engine: single-file SQLite, synchronous=FULL (project pattern).
OD-CA-B entropy: iterated S1 digests (no random module — probe-enforced).
OD-CA-C amounts: integer cents; tax rate 0.08 declared in the template;
        HALF_UP at the cent boundary; canonical decimal strings only.
OD-CA-D version identity: content-addressed (manifest fingerprint IS the id).
OD-CA-E module layout: model.py / generator.py / store.py / service.py /
        __init__.py under kandoo/src/corpus/ (project pattern).
OD-CA-F declared bound: entry_count ≤ 10000 (assembly-weight guard, declared).
OD-CA-G template dates: fixed 2026-06-15 (flake-window avoidance — declared).
OD-CA-H labels: engine-vocabulary field names; label_provenance literal
        "DECLARED-GROUND-TRUTH"; no canonical-model field mapping here.
OD-CA-I the corpus DB file lives ONLY where the caller points it; the package
        itself never derives paths from wall-clock or environment.
OD-CA-J the corpus store carries NO created_at/clock column — the whole
        package is clock-free (AST-probe-enforced); fingerprints and the
        content address are time-independent by construction.
```
